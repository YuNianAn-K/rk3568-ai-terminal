# RK3568 ↔ STM32 UART 协议草案

更新时间：2026-09-30（补充当前跟踪协议范围；保留基础与二进制草案）

## 状态与范围

- **已现场验证的文本协议**：RK3568 UART9 M1 ↔ STM32 USART1 的 `PING`、`LED?` 往返通信，115200 8N1，无流控。
- **已烧录并通过串口及肉眼验收**：`LED ON`、`LED OFF` 均返回 `OK`，随后 `LED?` 分别返回 `LED=ON`、`LED=OFF`；第二次演示时，用户确认 PC13 LED 先亮后灭。保持时间由脚本设为 10 秒，用户未单独计时。
- **已现场验证的文本边界行为**：未知命令返回 `ERR`，空行不回复，分段发送的 `PING` 仍返回 `PONG`。RAM-only 复测通过 25 次 `PING` 和 10 组 LED 开关与回读。
- **RK3568 当前启动状态**：UART9 M1 候选镜像已在明确授权后永久写入 boot 分区；整分区写后、热重启后，以及用户实际断电再上电后的 SHA256 均与候选一致。冷启动后 `/dev/ttyS9` 自动出现，`PING → PONG`、`LED? → LED=OFF` 通过；热重启后的完整文本序列和 PC13 目视闪烁验收也已通过。
- **规划中/未实现**：下文的二进制 CRC 帧协议及其全部命令。它不是当前固件可直接使用的协议。
- **后续已实现并用于现场实验**：当前固件还支持 PAN/TILT 手动控制与 TRK 跟踪会话。下面的 LED 表是基础子集，完整跟踪行为以本页补充、[云台 README](../apps/qt-ui/gimbal-joystick/README.md) 和 [当前交接](../HANDOFF.md) 为准。

## 当前文本协议

当前固件项目为 `stm32/firmware/stm32f103c8t6-uart-link/Project.uvprojx`，
RK3568 持久化启动后的设备节点为 `/dev/ttyS9`；`ttyFIQ0` 是 Linux 调试控制台，
不能用于这条链路。双方均使用 3.3V TTL UART，TX/RX 交叉、GND 共地，
不可把 5V 接到信号脚，也不可未经确认并联两端的 3.3V 供电。
请求和回复均为 ASCII 文本，以 `\r\n` 结束；空行不回复。

| 请求 | 回复 | 当前状态 |
| --- | --- | --- |
| `PING\r\n` | `PONG\r\n` | 已在硬件上验证 |
| `LED?\r\n` | `LED=ON\r\n` 或 `LED=OFF\r\n` | 已在硬件上验证 |
| `LED ON\r\n` | `OK\r\n`，PC13 低电平点亮 | 串口回复、状态回读与人工观察通过 |
| `LED OFF\r\n` | `OK\r\n`，PC13 高电平熄灭 | 串口回复、状态回读与人工观察通过 |
| 未识别的非空命令 | `ERR\r\n` | 已通过 `UNKNOWN` 命令现场验证 |

`LED?` 从 PC13 输出寄存器读取状态，而不是凭最近一条命令猜测。
当前文本协议没有 CRC、序号、ACK、重试或二进制帧，后续不能默认为已具备这些能力。

## 当前双轴跟踪补充（2026-09-30）

| 命令族 | 当前实现 |
| --- | --- |
| `PAN` / `TILT` | 手动脉宽控制、`CENTER`、`STOP` 及 `PAN?` / `TILT?` 状态回读；停止撤销 PWM，不代表轴被机械锁定 |
| `TRK POS?` | 返回 `TRK_POS=UNKNOWN` 或最后输出的 Pan/Tilt 脉宽；值只保留在 RAM，不是实际机械位置 |
| `TRK CENTER` | 显式初始化/回中位，返回 `TRK=CENTERING`；当前位置已知时沿斜坡推进 |
| `TRK ARM` | 当前位置未知时返回 `ERR TRK_POSITION_UNKNOWN`；已知时从保留脉宽建立目标并返回 `TRK=ARMED` |
| `TRK P+` / `P-` / `T+` / `T-` | 各轴目标按 80 µs 档位调整，目标有界，实际 PWM 最多按 24 µs/20 ms 向目标推进 |
| `TRK KEEP` / `TRK STOP` / `TRK?` | 刷新 2 秒会话超时、停止并撤销跟踪、查询 ARMED/OFF；失联超时停止双轴 |

当前跟踪范围为 Pan 500–2500 µs、Tilt 750–2250 µs；来源是当前装配动作记录，不是角度标定。重新上电时 PWM 关闭且保留位置未知。最新构建、实物反馈与配套回退在 `local/gimbal-resume-fix-20260930.md`，本次文档同步未重新烧录或硬件复验。

## 未来二进制 CRC 协议草案

## 设计目标

1. 在噪声、丢字节、重复帧和重启后可重新同步。
2. 将“已收到”与“已执行成功”分开确认。
3. 使状态改变命令可关联、可超时、可重试且尽量幂等。
4. 使安全策略留在 RK3568 上层；STM32 不执行自由文本或未定义命令。

## 帧格式

```text
+------+-----+---------+------+-------+-------+--------+---------+-------+
| SOF0 | SOF1| Version | Flags|  Seq  |  Cmd  | Length | Payload | CRC16 |
+------+-----+---------+------+-------+-------+--------+---------+-------+
| 0xA5 | 0x5A| 1 byte  |1 byte|2 bytes|1 byte |2 bytes | 0..256  |2 bytes|
+------+-----+---------+------+-------+-------+--------+---------+-------+
```

- `SOF0/SOF1`：固定帧起始；接收方应在校验失败后继续搜索下一组起始字节。
- `Version`：初始定义为 `0x01`；未知主版本必须拒绝。
- `Flags`：预留位必须为 `0`；未来可定义 ACK 请求、错误或分片标志。
- `Seq`：调用方递增的 16 位序号；重试必须复用同一 `Seq`。
- `Cmd`：命令或事件类型。
- `Length`：Payload 长度；超过上限、长度不符或 CRC 失败均丢弃该帧。
- `CRC16`：覆盖从 `Version` 到 `Payload` 的所有字节，不覆盖两个 SOF 字节。

本草案不定义转义机制。若后续实测显示 SOF 误同步风险不可接受，应在版本升级时增加 COBS、SLIP 或等价编码，而不是静默改变 `Version=1` 的解释。

## 确认、重试与超时原则

1. 接收方校验通过且接纳请求后，先回 `ACK`，回包必须复用原 `Seq` 并携带原 `Cmd`。
2. 无副作用查询可直接用 `RESULT` 返回，不要求单独 `ACK`。
3. `SET_OUTPUT` 等有副作用命令必须先 `ACK`，完成后再回 `OUTPUT_RESULT` 或 `RESULT`。
4. 发起方在等待窗口内未收到 `ACK` 时，最多重试固定次数；重试必须使用原 `Seq` 与相同 Payload。
5. STM32 必须在有限窗口内缓存近期已完成的 `(Seq, Cmd)` 结果，重复帧返回缓存结果，避免重复驱动执行。
6. 超时、掉线和重启后，RK3568 只能报告“结果未知”或重新查询状态，不能假定动作成功。

具体超时、重试次数、缓存窗口和持久化策略需由后续硬件时序与故障注入测试确定。

## 错误码原则

| 代码 | 名称 | 含义 |
| --- | --- | --- |
| `0x01` | `BAD_VERSION` | 不支持的协议版本。 |
| `0x02` | `BAD_LENGTH` | 长度非法或与命令不匹配。 |
| `0x03` | `BAD_CRC` | CRC 校验失败。 |
| `0x04` | `UNSUPPORTED_CMD` | 未定义或未启用的命令。 |
| `0x05` | `INVALID_ARGUMENT` | Payload 参数非法。 |
| `0x06` | `BUSY` | 当前不能接受新动作。 |
| `0x07` | `NOT_AUTHORIZED` | 上层未授权的危险动作。 |
| `0x08` | `HARDWARE_FAULT` | 外设或安全联锁故障。 |
| `0x09` | `EXECUTION_FAILED` | 命令被接受但最终执行失败。 |
| `0x0A` | `TIMEOUT` | 命令或设备侧操作超时。 |

密码、密钥、原始语音文本和任意 Shell 参数不得出现在 UART Payload 或错误字符串中。
